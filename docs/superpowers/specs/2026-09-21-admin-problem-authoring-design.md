# 管理端题目录入与发布设计（R16–R17）

## 目标

让内容组不用写 SQL 就能把一道题录进题库、存草稿、补来源、发布上线，并且在已发布题目改动时自动留下版本快照与审计记录。

对应 V1 规格里的 R16（录入与版本）与 R17（来源闸门），以及 OpenAPI 的 A19 `POST /api/v1/admin/problems`。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/admin/problems` | 录入、编辑、升版、发布，A19 已定义 |
| GET | `/api/v1/admin/problems` | 管理端列表，含草稿，本次新增 |
| GET | `/api/v1/admin/problems/{id}` | 编辑用详情，含答案与解析，本次新增 |

后两个接口 OpenAPI 原稿里没有：A19 只能写入，没有读回的口子，管理端就没法编辑已有题目，所以补上，并同步写进 `docs/openapi/openapi-v1.yaml`。

三个接口都先过 `CurrentUser.requireAdmin()`。非管理员拿到 403 `FORBIDDEN`，未登录拿到 401，和现有接口的口径一致。

## 版本规则

`problem` 存题目头（标题、题型、难度、年级、状态），`problem_version` 存内容快照（题干、选项、答案、解析、判题配置、满分）。两者的分工决定了升版时机：

- 只改标题、题型、难度、年级、知识点、来源，不产生新版本。
- 题干、选项、答案、解析、判题配置、满分中任意一项变化，追加一条 `problem_version`，`version_no` 取 `MAX + 1`，并把 `problem.current_version_id` 指向新版本。
- 内容没变就不建新版本。这条不是为了省行数：`submission` 记着作答时的 `problem_version_id`，错题本用它算 `versionChanged`。无脑升版会把所有历史提交标成"题目已更新"，那个提示就废了。
- 内容比对用 Jackson 的 `JsonNode.equals` 比 JSON 字段（对象键顺序不影响判断），题干与解析比字符串，满分比整数。
- 已发布题目的内容变更必须填 `changeNote`，草稿阶段可以不填。改了线上题却不说为什么，后面回溯纠错就没有线索。

`current_version_id` 始终指向最新版本，是否对外由 `status` 决定。搜索与详情接口都要求 `status = 'PUBLISHED'`，所以草稿的版本指针不会漏出去。

## 来源闸门

`publish=true` 时按 `origin_type` 校验必填项，缺一项就 400 `VALIDATION_ERROR`，题目留在 `DRAFT`：

| originType | 发布前必填 |
| --- | --- |
| ORIGINAL | 无 |
| ADAPTED | `rewriteNote` 改编说明 |
| LICENSED | `licenseRef` 授权凭证 |
| PUBLIC | `sourceUrl` 公开来源链接 |

草稿阶段只要求 `originType` 本身合法，先录内容、后补授权是真实的工作顺序，不该在草稿阶段就卡住。

`publish=false` 不会把已发布的题目降回草稿。下线需要的是 `HIDDEN` 状态和一个独立动作，本次不做，避免"忘记勾选发布"就把线上题撤了。

## 答案自检

录入时最容易出的事故是答案 JSON 写成判题器读不懂的形状——保存时一切正常，学生做题时判题直接抛异常。所以这里不另写一套格式校验，而是把标准答案当成用户答案喂给对应的 grader 跑一遍，判不出全对就拒绝保存：

- SINGLE / MULTI / JUDGE / NUMERIC：标准答案与用户答案形状相同，直接自测。
- BLANK：标准答案每空可以有多个可接受写法 `{"blanks":[["12","十二"],["24"]]}`，取每空第一个写法拼成用户答案再自测。
- 选择题额外要求答案里的选项键必须出现在选项列表里，键不重复、至少两个选项。答案填 E 而选项只到 D，这题永远做不对。
- `GraderException` 统一转成 400，带上判题器给的原因。

这样校验规则和线上判题逻辑天然同源，判题器改了容差或空序策略，录入校验跟着变，不会出现两套规则打架。

## 审计

题目落到 `PUBLISHED` 时往 `audit_log` 追加一条 `PROBLEM_PUBLISH` / `PROBLEM` / `problemId`，`detail_json` 记 `versionNo`、`changeNote` 与本次是不是新版本。两种情况都写：首次发布，以及已发布题目上线了新版本。只改标题这种不升版的编辑不写审计，避免日志被日常微调淹没。

## 管理员账号

现在没有任何途径产生 ADMIN 用户：种子数据里的 `content@mathematics.local` 是 ADMIN，但 `password_hash` 故意写成非法 BCrypt，登不进来。

开发环境在 `DemoUserInitializer` 里加一个能登录的 `admin@mathematics.local` / `admin12345`，和演示账号共用 `mathematics.dev.seed-demo-user` 开关。mysql profile 下该开关为 false，第一个管理员要手工提权：

```sql
UPDATE `user` SET role = 'ADMIN' WHERE email = '你的邮箱';
```

生产环境不该由代码凭空造管理员，所以这条提权语句只写在文档里，不做成开关。

## 前端

顶部导航在 `me.role === 'ADMIN'` 时才出现"管理"入口，普通用户看不到，未登录也看不到。

管理页分两块：左侧是题目列表（状态徽章 + 题型 + 难度 + 更新时间，可按状态筛选），右侧是录入表单。表单字段按录入顺序排：标题、题型、难度、年级、知识点多选、题干、选项、答案、解析、满分、判题配置、来源、变更说明。

表单遵循现有无障碍口径：

- 每个控件都有 `<label for>` 关联，不用 placeholder 当标签。
- 题型切换时只显示该题型需要的答案控件：选择题给选项行与键位勾选，判断题给是/否，数值题给数值与容差，多空题给按空分行的输入框。
- 提交失败时把后端返回的 `message` 显示在表单顶部的错误区，`role="alert"` 让读屏软件播报，而不是只弹一个 toast。
- 两个动作按钮分开：`保存草稿` 与 `发布`，发布按钮在来源必填项为空时不禁用，而是提交后由后端闸门给出具体缺哪一项——禁用按钮不告诉用户原因，是这类表单最常见的体验坑。
- 颜色不作为唯一信息载体：草稿与已发布的徽章除了配色差异，文字本身就写着状态。

选项、答案、判题配置在前端组装成后端约定的 JSON，不引入任何表单库或富文本编辑器，题干与解析就是 Markdown 文本域，复用现有的渲染管线预览。

## 验证

- 集成测试覆盖：非管理员被拒、缺来源字段不能发布、补齐后能发布、内容不变不升版、内容变更升版且写审计、已发布题改内容不填 changeNote 被拒、答案格式非法被拒、选择题答案键不在选项里被拒、发布后题目能被公开搜索接口搜到。
- 前端契约测试覆盖管理页的关键结构与无障碍属性。
- 全量 `mvn test` 不回归。
- MySQL profile 实跑一遍，确认录入链路在真实 MySQL 上也通（JSON 列与 `problem_source` 的 upsert 是两边差异最大的地方）。

## 范围外

- A20 批量导入（R19，规格里本就是 P1）。
- A21 纠错处理与回溯重判（R18），独立里程碑。
- 资料模块的上传与发布。
- 题目下线 / `HIDDEN` 状态与软删。
- 富文本或公式可视化编辑器，题干仍是 Markdown + LaTeX 手写。
